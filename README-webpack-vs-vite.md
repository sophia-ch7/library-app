## Порівняння webpack і Vite (на прикладі цього проєкту)

Проєкт: невеликий SPA на TypeScript + Bootstrap, без фреймворку. Спочатку зібраний на webpack (гілка `main` до міграції), потім перенесений на Vite (гілка `vite-migration`). Нижче наведено вимірювання, зроблені на моєму комп'ютері (Windows, одноразовий запуск кожної команди), та спостереження під час роботи.

### Результати вимірювань

| Параметр | webpack | Vite |
|---|---|---|
| Час продакшн-збірки (`npm run build`) | 33,5 с | 1,0 с |
| Розмір результату | `bundle.js` 322,3 КБ (JS і CSS в одному файлі) | `index.js` 94,6 КБ + `index.css` 224,7 КБ = 319,3 КБ |


### Швидкість

Продакшн-збірка у Vite виявилась приблизно у 30 разів швидшою (1 с проти 33,5 с). Для розробки це суттєво: збірку можна запускати без роздумів. Dev-сервер Vite не збирає весь проєкт наперед, а віддає браузеру модулі за запитом, тому старт і оновлення залежать від розміру проєкту значно менше, ніж у webpack. Різницю в HMR у такому маленькому застосунку я візуально помітила слабко: обидва варіанти оновлювали сторінку майже миттєво.

### Розмір збірки

Загальний розмір майже однаковий (322 КБ проти 319 КБ), бо основну вагу дає CSS Bootstrap, а не наш код. Тобто від вибору збирача розмір для такого проєкту майже не залежить. Відмінність у тому, що Vite віддав JS і CSS окремими файлами, що зручніше для кешування браузером, а webpack за моєї конфігурації вбудував стилі в JS через `style-loader`.

### Складність налаштування

**webpack.** Для цього проєкту довелося встановити сім пакетів (`webpack`, `webpack-cli`, `webpack-dev-server`, `ts-loader`, `css-loader`, `style-loader`, `html-webpack-plugin`) і написати конфігурацію приблизно на 25 рядків: `entry`, `output`, правила для `.ts` і `.css`, плагін для HTML, `devServer`. Потрібно розуміти, що саме робить кожен loader і в якому порядку вони виконуються (справа наліво). Під час налаштування виникла проблема сумісності: найновіша версія TypeScript не працювала з `ts-loader` (помилка `Cannot read properties of undefined (reading 'fileExists')`), і довелося вручну повернути TypeScript на гілку 5.x.

**Vite.** Достатньо одного пакета (`vite`) і конфігурації приблизно на 10 рядків (порт, папка збірки, `base`). TypeScript та імпорт CSS працюють «з коробки», окремих loader-ів не потрібно. Єдина зміна в `index.html`: тег `<script type="module" src="/src/index.ts">` для вказання точки входу (замість `HtmlWebpackPlugin`). Конфліктів версій під час міграції не виникло.

### Підключення UI-фреймворку та TS

У webpack Bootstrap підключається через імпорт у коді, але для цього треба окремо налаштувати обробку CSS (`css-loader` + `style-loader`) і TypeScript (`ts-loader`). У Vite той самий `import 'bootstrap/dist/css/bootstrap.min.css'` працює без додаткових налаштувань, що зменшує кількість місць, де можна помилитись.

### Екосистема плагінів

Екосистема webpack більша й старша: для нього існує loader або плагін майже для будь-якої нестандартної задачі, і він дає тонке керування збіркою. Екосистема Vite менша, але для типових задач (TypeScript, CSS, фреймворки, збірка під статичний хостинг) її вистачає, а плагіни простіші в підключенні.

### Висновок

Для невеликих SPA-проєктів, подібних до цього, Vite зручніший: менше пакетів і конфігурації, швидша збірка, менше проблем із сумісністю версій. Розмір готового застосунку від вибору збирача практично не змінився. webpack доцільно обирати там, де потрібне гнучке налаштування збірки або підтримка складних чи застарілих сценаріїв; саме в цьому його сила, але для простого проєкту вона перетворюється на зайву складність.
